## Commands

```bash
npm run dev     # dev server at http://localhost:3000
npm run build   # production build (also the main type-check)
npm run lint    # eslint (flat config, eslint-config-next)
```

There is no test suite. `next.config.ts` allows `*.trycloudflare.com` as a dev origin so the dev server can be shared through a Cloudflare tunnel for multiplayer testing.

## What this is

**Talo**: social games to play together — in pairs, with friends, in groups or solo. The core flow is: pick a game, create a room, send the link (WhatsApp), others tap it, type a name and play; no sign-up. The home (`app/page.tsx`) shows featured games and the catalog by shelf (`CATEGORIES`), filtered "Para jugar" by `PlayContext`. Each game has a lobby at `/{game}` and rooms at `/{game}/[roomId]`; games so far: `rompecabezas` (collaborative/versus jigsaw), `memotest` (pairs), `tutti` (Tutti Frutti, at `/tutti-frutti`), `dibujo` (Dibujá y adiviná), `codigo` (Código secreto, at `/codigo-secreto`), `deslizante` (sliding puzzle race), `cuatro` (4 en línea, at `/4-en-linea`), `palabra` (Palabra secreta, a Wordle race, at `/palabra-secreta`), `trivia`, `impostor` (El impostor), `naval` (Batalla naval, at `/batalla-naval`), `probable` (¿Quién es más probable?, at `/quien-es-mas-probable`), `conoces` (¿Cuánto me conocés?, at `/cuanto-me-conoces`), `generala`, `emojis` (Adiviná con emojis, at `/adivina-con-emojis`), `verdades` (Dos verdades y una mentira, at `/dos-verdades-una-mentira`), `damas`, `cajas` (Puntos y cajas, at `/puntos-y-cajas`), `reto` (Verdad o reto, at `/verdad-o-reto`), `mimica`, `ahorcado`, `sopa` (Sopa de letras, at `/sopa-de-letras`) and `carreras` (2D racing on a shared screen, phones as controllers) and `carreras3d` (Carreras 3D, at `/carreras-3d`: on a shared screen or each on their own phone) and `arena` (Arena medieval, at `/arena-medieval`: 3D knights, 1v1 to 3v3, optional bots), `yonunca` (Yo nunca nunca, at `/yo-nunca`), `onda` (En la misma onda, at `/en-la-misma-onda`), `telefono` (Teléfono descompuesto, at `/telefono-descompuesto`), `ludo` (Parchís, at `/parchis`; `/ludo` redirects there), `lobo` (Hombre lobo, at `/hombre-lobo`), `ajedrez`, `chinchon`, `truco`, `fuego` (Fuego cruzado, at `/fuego-cruzado`: a Halo-style first-person shooter), `otelo`, `backgammon`, `oca` (Juego de la Oca, at `/juego-de-la-oca`), `domino`, `pasteleria` (a 3D cake-making game, at `/pasteleria`: solo levels, or a timed duel in a room), `vibora` (Viborita, at `/viborita`: slither-style snakes, in public online worlds or a friends' room) `triqui` (tic-tac-toe, also called ta-te-ti, with an "infinito" mode) `tronco` (El tronco, at `/el-tronco`: a 3D ring where a spinning log has to be jumped or kicked back; vs bots, online or friends), `puentes` (cross every bridge once: generated maps, solo levels/daily, race rooms and online) and `ladrillazo` (a brick breaker: solo campaign/infinite, race, attack, duel and co-op, in friends' rooms or online) and `minigolf` (generated holes; solo course, today's holes, friends' rooms and online, everyone on the same hole at once) and `empujones` (talos pushing each other off a shrinking island, on a big screen with the phones as controllers) and `golpe` (El gran golpe, at `/el-gran-golpe`: a 2D top-down heist, stealing diamonds past guards, cameras and lasers, everyone for themselves or red vs blue, with bots). UI text is in Spanish (rioplatense voseo: "Subí", "Elegí") — keep that tone.

Stack: Next.js 16 App Router + React 19, Tailwind v4, Konva/react-konva for the puzzle board, Firebase Realtime Database + Storage. **There is no backend of our own** — everything runs client-side, except one route handler that signs voice-chat tokens (`app/api/voz/token`). Firebase config comes from `NEXT_PUBLIC_FIREBASE_*` env vars (in `.env`, gitignored); when missing, pages render `FirebaseSetupNotice` instead of crashing. The Firebase project is `talo-play` (`.firebaserc`); rules live in `database.rules.json` / `storage.rules`. The Storage bucket needs the CORS config in `cors.json` (applied with `gcloud storage buckets update gs://talo-play.firebasestorage.app --cors-file=cors.json`, not by `firebase deploy`) because the puzzle loads its image with `crossOrigin` to cut it on a canvas.

## Architecture

### Shared by every game

- **Identity** (`hooks/useClientIdentity.ts`): random client id + player name in `localStorage` (`salon.*` keys, migrated from the old `rompecabezas.*`), shared across games. The name is asked only when about to play: lobbies via `PlayerIdentity`, rooms via `NamePrompt invitedTo=…` (tells invitees which game they're joining). The home never blocks on it.
- **Accounts and friends** (`lib/account.ts`, `components/AccountProvider.tsx`, `components/FriendInvite.tsx`, `app/amigos`): optional — playing never needs one. Firebase Auth with Google only (popup, redirect if blocked; in-app browsers like TikTok/Instagram get a "abrí en tu navegador" note). `AccountProvider` (root layout) makes the profile on the first sign-in from the device's client id and name, keeps `status/{uid}` online (`room`/`game` from `RoomHeader` via `setActivity`), and shows invites as a card with "Unirme". On another device the account's client id and name are adopted (`adoptIdentity`), keeping the device's own id in `salon.deviceId`; signing out gives the device its own id back (or a new one, `dropAccountIdentity`), so it's no longer the account's player — never while on a room path (`isRoomPath`), where the id is the player's seat. Data: `profiles/{uid}` (name, clientId, code), `codes/{code}` → uid (friend codes, 6 chars), `requests/{to}/{from}`, `friends/{a}/{b}` (both sides, written on accept), `blocks`, `status` (friends only), `invites/{to}` (friends only). Unlike `rooms/`, these paths are locked down in `database.rules.json` — deploy rules with `firebase deploy --only database`. `/amigos?agregar=CODE` prefills a friend code (the shared link). Rooms get "Amigos" in `RoomHeader` and a friends list in `InviteCard`; light pages get `FriendsLink` (with pending requests) in `SiteHeader`.
- **Community** (`app/ideas`, `lib/community.ts`, `components/IdeasButton.tsx`): `/ideas` lets people vote the next game (`CANDIDATES`, toggles at `community/votes/{candidate}/{clientId}`, public and informal) and send ideas/improvements/bugs to `feedback/{pushId}`, which is write-only (read it in the Firebase console). `SiteFooter` brings a floating "Ideas" button to every light page; the first time, after a while, it shows a bubble once (`talo.ideas.visto`). Rooms don't get it. Both paths have their own rules in `database.rules.json`.
- **La Plaza** (`lib/plaza.ts`, `components/PlazaProvider.tsx`, `PlazaDrawer.tsx`, `PlazaButton.tsx`, `PlazaBanner.tsx`, `PlazaCallButton.tsx`): Talo's global chat, to find people to play with, as a drawer over any page (from the right on wide screens, from the bottom on phones) — not a page: `PlazaProvider` (root layout) holds it, `usePlaza().show(where)` opens it (the floating "Plaza" button bottom left on light pages via `SiteFooter`, the home's `PlazaBanner`, a waiting room, or `?plaza=1`; `/plaza` redirects there). Tabs: Chat (rooms looking for players on top), Gente (who's in, rules) and Admin. The provider also counts everyone on Talo: each tab writes `online/{clientId}/{tab}` = true (removed on disconnect; people, not tabs, are counted, with or without an account); `useActiveCount` shows it on the button, the banner and the drawer. Quick phrases (`PLAZA_PHRASES`, stored by index: append only) work for anyone; free text needs a Google account, not banned. Waiting rooms have «Buscar gente en la Plaza» (`plaza/calls/{roomId}`, card with "Unirme", gone when the waiting room closes or after `CALL_TTL_MS`). The rules are the safety (no backend): every post writes `plaza/last/{clientId}` = now in the same update and must be 2.5 s after the previous one; text rejects links, mails, @ and 7+ digit numbers (the client checks the same with `hasContact` and covers insults with `softenText`); the "Admin · Talo" badge (`admin: true`) and deleting, banning (`plaza/bans/{uid}`) and pinning (`plaza/pinned`) are only accepted from accounts in `admins/` (set from the console or `firebase database:set /admins/{uid} true`). `HIDE_AT` reports (`plaza/reports`, anyone) hide a message until an admin restores it; muting is local (`talo.plaza.silenciados`). Messages over a day old and stale calls are deleted by whoever opens the Plaza (`cleanupPlaza`)..
- **Open rooms** (`lib/openRooms.ts`, `components/RoomAccess.tsx`, `components/OpenRoomsList.tsx`): `rooms/{id}/meta/access` is "privada" (default/absent: link, code, or while it asks the Plaza for people) or "abierta" (listed the whole time, also mid-game; latecomers enter like any link). Chosen in the waiting room (`RoomAccessCard`, "¿Quién puede entrar?") or mid-game from the lock/globe in `RoomHeader` (`RoomAccessButton`), by the host or anyone when there's no host or it's away. The listing `openRooms/{id}` (game, count, `playing`, host name) is rewritten every `BEAT_MS` by the room's connected player with the lowest id; the writer also sets it to go on disconnect, takes it down when leaving alone and re-lists it if it vanishes while it stays (`onUnlisted`); readers skip it after `TTL_MS` and delete very old ones; the rules accept it only while the meta says "abierta". `playing` = no `WaitingRoom` on screen (`markWaiting`). The 3D games' full-screen matches have no header, so their room clients render `OpenRoomBeacon`. Not offered where `RoomHeader` gets `social={false}` (public worlds, solo rooms). "Salas abiertas" (`OpenRoomsList`: open rooms + Plaza calls, `subscribeListedRooms`) shows on the home, each lobby (that game) and the Plaza's Chat tab.
- **Friend chats** (`lib/dm.ts`, `components/FriendChat.tsx`): `dms/{a}/{b}/{pushId}` with the uids sorted, readable by those two and writable only while they're friends; `dmSeen/{me}/{other}` marks it read. `useUnreadChats` feeds the dot on each friend in `/amigos` and the badge of `FriendsLink` (with friend requests).
- **Game catalog** (`lib/games.ts`, pure data — safe in server components): per game `title`, `tagline`, `min/maxPlayers`, `duration`, `contexts`, `howTo`; plus `CONTEXTS`, `GAME_ORDER`, `CATEGORIES` (the home's shelves: every game in exactly one — a new game needs one), `roomPath()`. It's the single source for home cards, lobbies, waiting rooms and link previews — add a game there first. Every room stores `rooms/{id}/meta/game` (older puzzle rooms have none = `rompecabezas`). Room codes are global: `/sala/[roomId]` looks the game up (`lib/roomLookup.ts`) and redirects; the home's "¿Te invitaron?" (`JoinRoomForm`) and old links use it. Each room client redirects to `/sala/{id}` if the meta is another game's.
- **New games** (`lib/newGames.ts`, `components/NewBadge.tsx`, `components/NewGameBubble.tsx`): a catalog `addedAt` (release day, Argentina) makes a game "new" for `NEW_DAYS` (21) — set it when adding a game. While new it gets a yellow «Nuevo» `NewBadge` (home cards and rows, lobby band, similar games, landings) and a card in the home's "Juegos nuevos" row (newest four, hidden when none). Both are worked out in the browser after mount (`useNewGames`), so static pages never freeze the build day. `NewGameBubble` (in `SiteFooter`, over the Ideas button) tells people who played before (they have a name) about the newest one, once (`talo.nuevo.visto`); first visits are marked silently, its own lobby counts as seen, and the Ideas bubble waits while it is pending.
- **Host**: `meta.hostId` = the creator's client id (passed to each `create…Room`). Only the host sees "Empezar", unless there is no host (older rooms) or the host isn't connected — then anyone can (`startPermission` in `components/WaitingRoom.tsx`), so a room never gets stuck.
- **Inviting** (`lib/share.ts`, `components/InviteCard.tsx`): big code + WhatsApp (`wa.me`) + native share sheet + copy link, using the game's room URL. `RoomHeader` always has "Invitar". Link previews: `app/opengraph-image.tsx` (brand image) and `generateMetadata` → `lib/inviteMetadata.ts` in every `[roomId]/page.tsx` ("¡Te invitaron a jugar X!"). `metadataBase` comes from `NEXT_PUBLIC_SITE_URL` (default https://taloplay.com, the site's domain).
- **SEO / GEO** (`lib/seo.ts`): every game folder has a `layout.tsx` with `gameMetadata(id)` + `gameJsonLd(id)` (schema.org `VideoGame`, `BreadcrumbList` and the game's `FAQPage` from `gameFaq`) — a new game needs one too. Lobbies (`GameLobby`) always render — also on the server, name or not — how to play, the full guide (`GuideBody light`, under "Reglas de…"), the FAQ and similar games; only the create form waits for a name, so crawlers read the whole page. Each game has its own link preview, `/og/{game}` (`app/og/[game]/route.tsx`: its `GameArt` scene, serialized with `lib/svgString.ts`, on its shelf's color), used by its lobby and by its rooms' invites. Landing pages for searches (`lib/landings.ts`: one per `PlayContext` and one per shelf, texts and game lists built from the catalog; each is a folder `app/{slug}/page.tsx` → `LandingPage`; a new shelf needs an entry) are linked from the footer's game directory (every light page lists every game), the home's shelves and each lobby. The home (`app/page.tsx`, server; the UI is `app/HomeClient.tsx`) adds `HOME_FAQ` (shown and sent as `FAQPage`). `app/sitemap.ts`, `app/robots.ts` and `/llms.txt` are built from the catalog. Rooms are `noindex` (`inviteMetadata`). Google Analytics (`@next/third-parties`, id `G-22BJ9CB5Y7`, overridable with `NEXT_PUBLIC_GA_ID`) loads only in production builds.
- **3D quality** (`lib/postfx.ts`, `hooks/useQuality.ts`, `components/QualityButton.tsx`): the 3D games (Fuego cruzado, Arena medieval, Carreras 3D) take `quality` "alta" (bloom via `Bloom` + real-time shadows) or "baja"; it's remembered per game (`fuego.calidad`, `arena.calidad`, `carreras.calidad`), defaulting to high with a mouse and low on touch. Bloom threshold is ~1, so only colors pushed over 1 on purpose (`glowColor`: flames, lights, brake lights, visors) glow — keep plain whites at or below 1. Lights used by effects are created up front (no shader recompiles mid-game). Carreras only blooms a single full-canvas view (split screens draw plain).
- **Brand** (from a design handoff kept out of the repo, `talo-handoff/` locally; code comments citing it refer to that): Talo's own pages (home, lobbies, the name prompt) are light (`.talo-light`, white page, yellow `#FFD400` hero, flat category colors); rooms and games stay dark on the ink page (`#111111`). Tokens are Tailwind colors in `app/globals.css` (`bg-talo-hero`, `text-talo-ink`, `bg-talo-surface`…). Fonts: Albert Sans (UI), Dela Gothic One (`font-display`: titles, logo, big numbers; one weight, so `font-synthesis-weight: none`), JetBrains Mono (`font-code`, room-code boxes), Geist Mono (`font-mono`, in-game numbers). No gradients, glows, glassmorphism or tilted elements. Each shelf has a flat color (`CATEGORY_COLORS`, `gameColors(game)` in `lib/talos.ts`), used by lobby bands, the waiting room's table and `GameIcon`.
- **Talos** (`components/Talo.tsx`, `lib/talos.ts`, `lib/taloEvents.ts`): the brand's characters, flat shapes with eyes and expressions. A player's talo is `playerTalo(id, color, size)`: shape from the client id, body in the player's color, the same on every screen. They are a read-only layer: game engines never import them, and they only react to public events through `reduceTalos` (`player_joined` in `TaloTable`, the waiting room's table; `game_ended`/`round_ended` in `GameResults`). Games with hidden info (`HIDDEN_INFO_GAMES`) only allow joins/turns mid-match (`eventAllowed`). Never feed them roles, hands, secret words, hidden positions, unrevealed scores or decision times.
- **Icons**: presentation UI (headers, waiting room, rules) uses `lucide-react` icons, not emojis — game icons live in `components/GameIcon.tsx` (`GameIcon`, a flat tile in the game's shelf color; `CONTEXT_ICONS`). Emojis inside the games are game content and stay.
- **Instructions** (`lib/guides.ts`, `components/HowToPlay.tsx`, `components/GuideArt.tsx`): every game has a full guide (goal, numbered sections, tips) besides the catalog's three-step `howTo`. Sections may name an `art` — a small inline SVG diagram drawn by `GuideArt`. The guide shows in the lobby ("Ver las reglas completas"), in the waiting room ("Cómo se juega") and from the "Reglas" button every `RoomHeader` has, also mid-game (`RulesDialog`). A new game needs a guide.
- **Room settings** (`components/RoomSettings.tsx`, `lib/roomSettings.ts`): a game's settings are declared once as a `GameSettings<T>` (in `app/{game}/settings.tsx`, or `components/{game}/settings.tsx` for the 3D games and carreras): fields (`choice`, `multi`, `toggle`, `custom`, `note`), `problem`, `create`, `save`, `fromMeta`. The lobby renders it with `CreateRoomForm`; the waiting room gets `RoomSettingsEditor` through `WaitingRoom`'s `settings` prop, shown to whoever may start (`startPermission`). `saveRoomSettings` writes the meta (and any fields a game copies into its state, e.g. Parchís `rules`, Truco/Dominó `target`, Backgammon `matchTo`, Oca `dice`, Fuego `map`/`mode`) only while the state is `waiting` (Verdad o reto: anytime). Room clients follow the meta live with `watchRoomMeta` (not a one-time `get`), so everyone sees the change. After a game, `BackToRoomButton` (`backToWaiting`: status `waiting`, `gameNo` + 1, a new `seed`) brings the room back to change settings; start functions must therefore build a fresh game from any leftover state. Rompecabezas has no waiting room, so its settings stay fixed. Games without settings keep their simple create form.
- **UI pieces**: `TaloLogo`/`TaloMark` ("tal" + a talo as the "o"; `tone` ink on light pages, hero yellow on dark), `SiteHeader`/`SiteFooter` (nav inside each light page's colored hero; black footer with the giant wordmark), `HeroCrowd` (the home's talos, pupils follow the cursor unless reduced motion), `GameArt` (each game's illustration: talos doing that game, flat SVG on a 120×120 canvas with no background, shown on the shelf color as the catalog thumbnail, the featured cover and the lobby band — a new game needs a scene), `JoinRoomForm` (code typed over six boxes; codes have letters and digits), `GameLobby` (band in the shelf's color, name, the game's create form as children on an ink panel since it shares the rooms' dark controls, how to play), `WaitingRoom` (pre-game screen: the table of talos with the host tagged, settings summary, `InviteCard` with the code in boxes, how to play, start), `RoomHeader`, `RoomStatus`, `DieFace` (a die with the roll animation), `GameResults` (`components/Results.tsx`: the end screen for scored games — podium, ranking with shared places, `rankFrom(players, scores)`; board games keep their own banner over the final board and add `Confetti` when you win), `components/ui.ts` (shared Tailwind class strings). One-on-one board games (Otelo, Backgammon) share their seat logic: `lib/twoSeats.ts` (pure join/take/leave/swap over `seats.a/b`, run inside each game's transaction) and `components/TwoSeatPicker.tsx` (seats in the waiting room, `Spectators`, `seatName`).
- **Full screen and zoom** (`lib/fullscreen.ts`, `components/FullscreenButton.tsx`, `app/manifest.ts`, `components/ZoomGuard.tsx`): every game's full-screen button is `FullscreenButton` (Fullscreen API with the `webkit` fallback on Android, iPad and computers; on iPhone, which has none for pages, it explains "Agregar a inicio"; hidden when already running from the home screen). The manifest (+ `appleWebApp`) makes Talo open as an app from the home screen. Page zoom stays off for the games: the viewport says `user-scalable=no` (Android), `ZoomGuard` cancels iOS's pinch gesture and `touch-action: manipulation` on `html` drops double-tap zoom; games that zoom themselves (the puzzle) still get their touches.
- **Turn alert** (`hooks/useTurnAlert.ts`): turn-based games call `useTurnAlert(myTurn)` (before any early return): a short vibration when the turn arrives and a blinking "¡Te toca!" tab title while the page is hidden.
- **Sounds** (`lib/sfx.ts`, `hooks/useSound.ts`): short synthesized effects for the 2D games (`playSound`: place, capture, turn, good, bad, dice, tick, win, end, flip), muted from the header (`talo.sonido`, shared); the audio unlocks on the first tap. `useSoundOn(key, name)` plays when a move counter changes (not on arriving). `useTurnAlert` chimes and `Confetti`/`GameResults` play win/end on their own. The 3D games and Pastelería keep their own audio.
- **Voice chat** (`lib/voice.ts`, `components/VoiceButton.tsx`, `app/api/voz/token/route.ts`): LiveKit Cloud (SFU). `RoomHeader` shows "Voz" (unless `social={false}`: Viborita's public worlds) when `NEXT_PUBLIC_LIVEKIT_URL` is set; the route — our only server code — signs the token with `LIVEKIT_API_KEY`/`LIVEKIT_API_SECRET` after checking via RTDB REST that the caller is in the room's presence and it isn't `meta.online`. LiveKit room = `talo-{roomId}`, identity = client id. The connection is a module singleton (survives header remounts and fullscreen 3D games); `VoiceKeeper` in the root layout leaves when the path no longer has the room code. Silencing someone is local (`setVolume(0)`).
- **Text chat** (`lib/chat.ts`, `components/ChatButton.tsx`): "Chat" in every `RoomHeader` (not with `social={false}`), plain pushes to `rooms/{id}/chat` (last 60 read, 200 chars, a short gap between sends), with an unread counter and a bubble for new messages. Games where typing gives the answer away pass `chatLocked` (a reason) during those phases: Dibujo `drawing`, Emojis `question`, Impostor `clues`/`voting`/`guess`, Mímica `acting`, Palabra `racing`, Lobo at night and for whoever sees every role (dead, spectators) mid-game. A new guessing game should do the same.
- **Most played** (`lib/playStats.ts`): `RoomHeader` (in every room) calls `countPlay`, which adds 1 to `rooms/_stats/plays/{game}` by transaction once per browser and room (localStorage `talo.jugada.{roomId}`). The home's "Los que más se juegan" is `mostPlayed(stats, 4, CURATED)`: the curated four until there are `MIN_PLAYS` in total. It sits under `rooms/` because that's what the rules open; keys starting with "_" are never rooms, and the cleanup skips them.
- **Tracking** (`lib/analytics.ts`, `components/PageViews.tsx`, `lib/dailyStats.ts`, `app/estadisticas`): GA events via `trackEvent` (typed list in `lib/analytics.ts`; production only). Page views on client navigation are sent by `PageViews` (root layout) once the new title is in, because GA's own history page views read the old title — GA's enhanced measurement "browser history events" must stay off. `PageViews` also `set`s `page_title` (so "¡Te toca!" never shows as a page) and counts the day's visit. Our own per-day counts live at `rooms/_stats/days/d{yyyymmdd}` (Argentina's day: `visits`, `new`, `plays/{game}` from `countPlay`, `rooms/{game}` from `create_room`), production only, bots skipped; the internal, unlinked, noindex `/estadisticas` page reads them and can mark a browser as the team's (`talo.noContar`: not counted, GA `traffic_type: internal`). `app/not-found.tsx` sends `page_not_found` with the path.
- **Presence** (`lib/presence.ts`, `hooks/useRoomPresence.ts`): connected players with name/color, removed via `onDisconnect`. An account shares one client id on every device, so two devices of one player share an entry: when one leaves and removes it, the other writes it back.
- **Old rooms cleanup** (`lib/roomCleanup.ts`): there's no backend, so visitors' browsers do it. `rooms/_index/{roomId}` = last activity (ms), touched by `joinPresence` on entering, every 30 min while connected and on disconnect. The home and every lobby call `cleanupOldRooms` (at most every 30 min per browser): it deletes up to 25 rooms idle for over `MAX_IDLE_DAYS` (3) with empty presence, and indexes up to 25 rooms from before the index (REST `shallow` listing + `meta/createdAt`). `_index` can't clash with a room code. Storage files are deleted by the bucket's lifecycle rule (`storage-lifecycle.json`, 10 days, applied with `gcloud storage buckets update gs://talo-play.firebasestorage.app --lifecycle-file=storage-lifecycle.json`), not by the app.
- **Seeded randomness** (`lib/random.ts`): `mulberry32`, `seededShuffle`. Anything derived from a seed stored in the room must stay deterministic across clients; changing it alters existing rooms.
- **No host**: shared game state (turns, rounds, races) is only mutated through `runTransaction` (`lib/transact.ts` wraps it with a normalizer), so concurrent clients can't double-apply a move. Timers/delays are scheduled by every client and made idempotent by the transaction (see `resolveMismatch`), so one player leaving can't freeze a game.

### Rompecabezas (`app/rompecabezas`, `lib/puzzleRoom.ts`)

- **Deterministic geometry** (`lib/puzzleGeometry.ts`): piece shapes (curved tabs) are generated from `rows`, `cols`, and `seed` in the room meta; geometry is never sent over the network.
- **Rendering** (`lib/piecesRender.ts`, `components/PuzzleStage.tsx`, `PuzzlePiece.tsx`): the image is clipped into per-piece bitmaps; `PuzzleStage` handles zoom/pan/drag and snapping (`SNAP_DISTANCE`). It's loaded via `next/dynamic` with `ssr: false` in `RoomClient` because Konva needs the DOM.
- **Room data** (`lib/puzzleRoom.ts`):
  - `rooms/{id}/meta` — image URL/size, rows/cols, seed, `mode` (`"colab" | "versus"`).
  - `rooms/{id}/pieces/{pieceId}` — `{x, y, placed, holder}` (colab). In versus mode each team (`lib/teams.ts`) has its own copy at `rooms/{id}/teams/{red|blue}/pieces`.
  - `rooms/{id}/race` — versus race state, mutated via `startRace`, `reportTeamFinished`. Winner detection runs in the browser of whoever places the last piece.
  - Image is uploaded to Storage at `rooms/{id}/image.jpg` after client-side downscale (`prepareImage`).
- **Piece locking**: dragging sets `holder` to the client id (`holdPiece`) with an `onDisconnect` cleanup; `releasePiece` writes the final state and cancels that handle. Pieces held by others or already `placed` are not draggable. Positions are written live during drag, throttled.

### Memotest (`app/memotest`, `lib/memotest.ts`)

### Carreras and Carreras 3D (`app/carreras`, `app/carreras-3d`, `components/carreras`, `lib/carreras*.ts`)

- Two catalog games on the same code: route pages just pass `game` to the shared `Lobby`, `RoomClient` and `ScreenClient`. `carreras` is always `pantalla` mode, drawn top-down in 2D. `carreras3d` draws in 3D and can also run in `telefono` mode.
- Up to 4 seats (`a`–`d`, like 4 en línea's). `meta.mode` picks where the race runs. In both modes `carreras/state` changes only by transaction. It holds `racers` (seats at the start), the `startedAt` countdown, `results` (ms per seat, `reportFinish` once each) and `firstAt`. The race closes when every racer finished, or `FINISH_GRACE_MS` after the first finish, or early if the rest left (`closeRace`, any client via `useRaceCloser`). `winner` = fastest.
- `pantalla`: a screen at `/carreras/{id}/pantalla` (TV/projector; the lobby sends the creator there) is the authority. It simulates every car from `carreras/input/{clientId}` (`{s, b}`, throttled by `useInputSender`, removed `onDisconnect`; no input = coast), reports each finish and writes `carreras/live` (lap/place) for the phones. It never joins presence, so phones see the host as away and anyone can start. View: top-down 2D (`lib/carrerasDraw.ts`: hills shade and cast shadows, bridges and the cars on them are drawn over the rest, flying cars grow) for `carreras`, split-screen 3D (1, 2 or 2×2) for `carreras3d`. A/D/S and the arrows drive seats a/b for testing.
- `telefono`: no screen. Each phone runs `PhoneRace`: it simulates its own car, publishes `carreras/cars/{clientId}` (`CarPose`, ~15 Hz, tagged with `gameNo`), and draws rivals extrapolated from their pose and eased. Collisions with rivals only push your own car (`collideWithGhost`). Each phone reports its own finish.
- `lib/carrerasTrack.ts` is pure: tracks are Catmull-Rom centerlines in their own world (`def.size`, 2000–2600 wide) with walls at half the width. `progress` (arc length driven) gives laps and places. Gas is automatic (`gas: false` coasts after the finish). `stepCar`/`collideCars`/`collideWithGhost` return the hit speed (for sound and sparks). Each track has a `theme` (campo, atardecer, desierto, nieve, noche) that only changes the looks.
- Mario Kart-ish features: control points may carry a height (`hs` per sample; hills slow you down going up), `ramps` and `boosts` are `TrackFeature`s placed by control-point index (+ fraction) and a side/span across the road, resolved to `Zone`s. `groundAt` = hills + ramp wedge. Cars have `z`/`vz`/`air`/`boost`: on the road they follow it unless it drops away faster than gravity (ramp lips, sharp crests), then fly ballistically with little steering; boost pads kick the speed up to `BOOST_TOP`. Parts of a track may cross when one is `BRIDGE_CLEARANCE` higher (`trackProblem` checks that, slopes, a flat start and the world bounds); cars at different heights don't collide. Track shapes were tuned by rendering them — keep `trackProblem` null for every fixed track.
- `aleatoria` track: `getTrack("aleatoria", seed)` generates it from `carreras/state.trackSeed` (set at creation; `newTrack` while waiting, `rematch(…, true)` = "Revancha en otra pista"). The generator places points around the center in angle order and keeps the longest of the first few that pass `trackProblem` (overlap, too tight, outside, short); same seed = same track on every client. Use `trackSeedOf(meta, state)`: it's 0 for fixed tracks so they never rebuild.
- Long tracks (`long: true`: Gran Premio, Cañón, Nocturna, ~14–16k long in 4200–4400 wide worlds) are 3D only (`tracksFor(is3d)`; `normalizeMeta` sends a 2D room back to the óvalo): from above their cars would be tiny. `city` (Nocturna) swaps most trees for lit buildings. Designing one is iterating points until `trackProblem` is null; `lapSeconds` estimates a lap.
- Bots: `meta.bots` (0–3) and `meta.botLevel` (fácil/normal/difícil) are copied into the state as `botCount`/`botLevel` (the start's transaction only sees the state). `raceFrom` fills that many free seats into `state.bots`; their `seats` entry stays "" so people can still sit while waiting (`isBotSeat` only counts during a race; `driverName` → "Rayo (bot)"). `botInput` (pure, `lib/carrerasTrack.ts`) aims at a point ahead on its own lane, pulled to the inside of the next bend and onto boost pads it likes, and brakes for the tightest bend within braking distance; levels scale corner margin, top speed, steering wobble and boost use; `pace` is a light rubber band against the people's leader. Pantalla: the screen drives them. Telefono: the bot host (lowest connected id) simulates them as real `Car`s and publishes `cars/bot-{seat}` (`sendBotPose`, no `onDisconnect`: the next host rebuilds them with `carFromPose`) and reports their finishes. `useRaceCloser` treats bots as present.
- Lap times: whoever runs a car keeps a `LapClock` and sends the best lap with `reportFinish(…, bestMs)` → `state.best`; `Standings` shows each best lap and marks the fastest. HUDs show the lap's time when it ends, "¡Última vuelta!" and "¡Contramano!" (`wrongWay`); the phone shows speed and the running lap clock, written straight into the DOM. In development `window.__carrerasAuto = true` drives your own phone car with the bot brain (for testing).
- `lib/carreras3d.ts` (three.js, browser only) builds the scene from the sampled centerline, dressed by the theme (gradient sky, clouds, stars/lamps at night, snowfall, cacti…, grandstand by the start, start lights via `setStartLights`). 2D (x, y) maps to (x, height, y) and `rotation.y = -heading`. Raised road sits on earth banks, or on a deck with pillars where it passes over another part (`bridgeSamples`); ramps are striped wedges and boost pads scroll their arrows. Wheel spin, steering, pitch, brake lights, tire smoke, landing dust, boost flames and sparks are derived from the poses alone (`setPose` with velocity, `z` and `ground`), so rivals get them too (phones send `z` and lift `l` in `CarPose`); `impact` adds a spark burst and camera shake. Cameras: behind (`detras`) or cockpit (`cabina`).
- Cars (`carGeometry`, built once per scene and shared, `userData.shared` skips disposal per car): a GT body extruded from its profile, fenders, glass cabin under a painted roof, splitter, skirts, diffuser, exhausts, wing, twin stripes in the seat's `accent` and the race number on the doors (`CarLook`: color, accent, number, label); merged per material. Track dressing: chevron boards and tire stacks on sharp bends (`buildCorners`, from `curvatures`), Talo ad boards along straights (`buildBillboards`), a second grandstand on long tracks, buildings (`buildCity`). Performance: adaptive resolution (`adapt` lowers the pixel ratio down to 60% when frames are slow), one shadow map per frame around every followed car (`shadowMap.autoUpdate = false`), runoff/curbs/lines/walls merged into one mesh, static objects' matrices frozen after `build` (mark anything that moves with `userData.moving`), name tags hidden when a car is right in front of the camera.
- Sound (`lib/carrerasAudio.ts`): everything synthesized with Web Audio — engines with gear shifts, tire screech, hits, jumps/landings, boosts, countdown beeps, lap chimes, finish fanfare. `RaceCues` turns per-frame facts into one-off sounds. The context resumes on the first tap/key, so `RaceAudio` lives for the whole page, not per track. Muted state in `localStorage` (`carreras.sound`). The screen plays every car (panned per split view); in telefono mode each phone plays its own car, plus nearby rivals more quietly.
- Controls (`components/carreras/Controller.tsx`): buttons, or tilt (gravity projected on the screen's x axis from `deviceorientation`; iOS needs `requestPermission` from a tap and HTTPS). It works as a page panel (pantalla) or as an overlay on the 3D view (telefono). On computers the keys drive too (arrows or A/D steer, down arrow, S or space brake; held keys win over tilt); with a fine pointer the overlay shows only a key hint instead of the big touch zones ("Usar botones" brings them back) and the panel adds the hint.

### Arena medieval (`app/arena-medieval`, `components/arena`, `lib/arena*.ts`)

It writes `empujones/live` (`out`, dash `hits` per player) so phones show "¡Al agua!" and buzz. WASD/space/Shift and arrows/L/K drive the first two people from the screen's keyboard, for testing.
- `lib/empujones.ts` is pure: bodies with mass (bracing ×3, burns `grip`), dash (impulse, `DASH_COOLDOWN`, a dash hit adds a push and stuns), elastic bumps, `islandRadius(t)` (whole until `SHRINK_FROM`, shrinks to `ISLAND_MIN_R`, sinks to 0 by `SINK_END` so every round ends), a fall when the center leaves the island, `pusherOf` for the feed, and `botInput` (gets between the target and the middle, dashes when lined up toward the water, backs off the edge, braces against dashes; three levels). Not deterministic and not shared: only the screen runs it.
- `empujones/state`: `roster` (connected people not `watching` + bots `bot0…`, up to 8; alone = one bot anyway), `colors` (own color unless taken), `round`, `startedAt` (countdown end; after a round it's `BETWEEN_MS` + `COUNTDOWN_MS` ahead, showing `lastRound`/`lastWinner`), `score` (rounds) up to `target`, `wins` (matches). While waiting the screen already puts everyone's talo on the island (falling respawns) and the phones' waiting room has the pad, to try the controls.
- Phone (`app/empujones/[roomId]/EmpujonesClient.tsx`, `components/empujones/Pad.tsx`): a floating stick (up = up on the TV), «Empujar» (counter, local cooldown fill) and «Aguantar» (hold, grip bar guessed locally); keyboard on computers. The press count survives the pad's remount (module map), and the screen ignores a count that went down (a reload). Drawing: `lib/empujonesDraw.ts` (flat canvas: water ripples, island with cliff/sand/grass, crumbs while it shrinks, talos with eyes, splashes, bump stars, names).

### El gran golpe (`app/el-gran-golpe`, `components/golpe`, `lib/golpe*.ts`)

- Game id `golpe`. A heist seen from above on a flat canvas, everyone at once for `meta.minutes`: pick up diamonds, carry them to an exit (only banked ones count), don't get caught. `meta.mode` `todos` (everyone for themselves, any exit) or `equipos` (red uses exits 0–1 on the left, blue 2–3 on the right; team totals win; teammates can't rob each other). Teams are picked while waiting (`chooseTeam`, `shuffleTeams`); `newMatch` sends the rest, then `meta.bots` bots, to the smaller team. Newcomers mid-match join (`joinGolpe` gives a team and a `slots` exit), up to `MAX_THIEVES`.
- `lib/golpeMap.ts` is pure and deterministic: `generateMap(seed, rows)` — RX×rows rooms of `ROOM` cells with one-cell walls, mirrored left/right (doors are picked by Kruskal over mirrored edge pairs, plus some loops), entrance rooms in the corners with a 2×2 exit, the vault(s) in the middle (big diamonds `BIG_GEM`, guard + camera + lasers on its doors), halls with guards/cameras. Security is a function of match time (seconds since `startedAt`), never sent: `guardAt` (a loop of walk + turn-at-the-corner segments), `camAngle` (sweep), `laserOn`. `gemAt(map, i, gen)` places diamond i after being taken gen times (mirror pairs share the dice). Changing the generator changes every room's map.
- `lib/golpeSim.ts`: box movement against walls (`moveBox`), bag slows you (`speedFor`), `exposure` (light cones with line of sight: guards fill the alert fast, cameras slower; touching a guard or a lit laser = caught at once) and `watch` (the alert meter). Bots: `thinkBot` runs a BFS where each cell is checked for light at the time the bot would reach it, picks diamonds by value/distance or the nearest own exit (`bankAt` by level, or when time is short), and hides in a cell that stays dark when nothing is safe (`escapeRoute` when cornered). Levels differ in look-ahead, ignoring cameras, pace and how often they rob.
- Same no-authority model as Viborita: each phone runs its thief and writes `golpe/poses/{id}` (~10 Hz); the bot host (lowest connected id) runs the bots (rebuilt from their pose by the next host). The score is `loot/g{n}/{id}` (`Loot`: bag, bank, robbed `sn`/`by`/`k`/`sat`, caught `cn`/`lost`), changed only by leaf transactions: `takeGem` (`gems/g{n}/d{i}` = `{n, at}`, back after `GEM_RESPAWN_MS`), `takeDrop`, `bankBag` (inside an allowed exit), `robThief` (up to `STEAL_TAKE`, victim shielded `STEAL_SHIELD_MS`), `getCaught` (half the bag falls as `drops/g{n}`; the runner handcuffs its thief `FROZEN_MS`, then sends it back to its exit, unseen for `SAFE_MS`). Everyone's feed comes from loot counters. Any client closes the match after `endsAt` with the synced loot (`closeGolpe` → `final`, `winTeam`, `wins`).
- Drawing: `lib/golpeDraw.ts` (`Painter`: the building cached offscreen with exits, vault rugs and paintings; light cones as visibility fans; lasers flicker before turning on; talos with a mask and a sack; guards with a cap; minimap). Controls: a floating touch joystick, WASD/arrows, «Robar» = space/E or the button (lit when someone is in reach). The camera follows your thief, clamped to the building.

### Dominó (`app/domino`, `lib/domino.ts`)

- Seats `a`–`d` like Parchís (two players sit opposite); four play in pairs (`a`+`c` vs `b`+`d`, `partnerOf`/`sameSide`), 2–3 have a boneyard (`stock`): no fitting tile → `drawTile` until one fits, `passTurn` only with it empty (the client passes by itself). Tiles are 2-digit codes concatenated; `line` is stored oriented so its ends are its first and last digit (`fits`, `place`).
- The first hand opens the highest double (`mustOpen`); later hands, the last winner. Going out scores the rivals' pips; everybody passing in a row is a tranque: fewest pips in a hand wins (a tie between sides scores nothing). `score` per seat (partners get the same), up to `meta.target`. `playForAbsent` plays/draws/passes for someone who left.

### Hombre lobo (`app/hombre-lobo`, `lib/lobo.ts`)

- Roles dealt at start (`wolvesFor`: 1–4 wolves, plus vidente and médico). `night → day → dusk → night…`: at night every living player picks a target (`nightAction`; villagers pick a decoy so tapping gives nothing away), resolved when all connected living players acted or `NIGHT_SECONDS` (`closeNight`: wolves' plurality, médico saves, no repeated protection, vidente's picks in `seerLog`). By day the living vote (`dayVote`, `NOBODY` allowed; a tie eliminates no one), `closeDay` on `meta.daySeconds`. `winnerOf` after every death. The dead and spectators see every role.

### Ajedrez (`app/ajedrez`, `lib/ajedrez.ts`, `lib/ajedrezRules.ts`)

- Seats like damas (`a` whites at the bottom, `b` blacks, board flipped). `ajedrezRules.ts` is pure and complete except threefold repetition: castling, en passant, promotion (`promo`, defaults to queen), check, mate, stalemate, insufficient material, 50 moves; verified with perft counts. The position (`cells` 64 chars, uppercase white, row 0 = rank 8, `castling`, `ep`, `half`) lives in the state; `makeMove` re-checks `legalMoves` in the transaction and appends Spanish notation (`toSan`: R D T A C) to `history`. Resign, draw offers and rematch with colors swapped like damas.

### Chinchón and Truco (`app/chinchon`, `app/truco`, `lib/baraja.ts`, `components/Naipe.tsx`)

- Spanish deck codes: suit (`o c e b`) + rank char (`1`–`9`, `A`–`C` = 10–12), jokers `x1`/`x2`; hands and piles are concatenated codes (`splitCards`). Decks are shuffled with Math.random inside the dealing transaction; hands are in the state (DevTools — accepted).
- Chinchón (`lib/chinchon.ts`, rules in `lib/chinchonRules.ts`): 48 cards + 2 jokers, 7 each; `drawCard` (deck or pile; the deck is rebuilt from the pile when empty) then `discardCard` (can't throw back the card just taken; `cut` only if `canCut`). `bestArrangement` searches melds (groups, same-suit runs, jokers with ≥2 real cards) for the fewest loose points; clean cut −10, chinchón wins on the spot, over `meta.limit` you're out.
- Truco (`lib/truco.ts`): sin flor, 1v1 (`ab`) or 2v2 (`abcd`, teams a/c vs b/d), to `meta.target`. `strength` is the card hierarchy, `envidoOf` the hand's envido (from the three dealt cards). Songs wait in `envidoAsk`/`trucoAsk` and block plays; `applyAnswer` handles quiero / no quiero / raises, including "el envido está primero" over a pending truco. `handWinner` resolves bazas with pardas; `goToDeck` gives up the hand; `playForAbsent` refuses a song nobody can answer or plays the first card of an absent player.

### Fuego cruzado (`app/fuego-cruzado`, `components/fuego`, `lib/fuego*.ts`)

- First-person shooter, free-for-all (`roster` side `"ffa"`) or red vs blue, 2–8 fighters (bots fill, three levels), on three maps (`lib/fuegoMaps.ts`: Búnker small, Fortaleza medium, Valle large). Maps are boxes + ramps + spawns + pickups + bot `nodes`; `solidBoxes` adds the boundary walls. Ends at `goal` kills (per player or team) or on time (`timeUp`).
- `lib/fuegoSim.ts` is pure: geometry (`groundAt` steps/ramps, `collide`, `rayWorld` with exact ramp wedges), `Soldier` movement, `WEAPONS` (rifle, pistola, escopeta, francotirador with zoom, lanzacohetes; `WEAPON_IDS` append-only since poses send the index), `Arsenal` (two slots, mags/reserve, reload, switch, grenades, melee — local to each phone, not in the state), `castBullet` (head sphere + body cylinder, falloff, `assist` cone for touch), `flyProjectile` (rockets, bouncing grenades — deterministic so every phone flies them the same), `blast`, `pickSpawn`, and the bots: `navGraph` (edges worked out from the geometry, directed so drops are one-way), A* and `botThink`.
- Same no-authority model as the arena: each phone runs its soldier and writes `fuego/poses/{id}` (~20 Hz; shot counter + last shot end so others draw tracers); the shooter decides hits and writes `damage`; rockets/grenades are published at `fuego/proj` and their `fuego/booms` explosion does the damage. The bot host (lowest connected id) runs the bots. Health and shield are in the state; the shield recharges on read (`shieldOf`: value at the last hit + time since `hitAt`), so nobody writes while it fills. The dead respawn after `RESPAWN_MS` (`respawn`, the phone picks the spot). Pickups are in the state (`pickItem`, come back after `RESPAWN_ITEM_MS`).
- `lib/fuego3d.ts` (three.js) builds the map by theme (sky, sun, clouds, ambient motes, glowing panels), armored soldiers from primitives animated from poses, the first-person weapon with arms in a second pass (sway, recoil, landing), tracers, muzzle-flash lights, bullet holes (`rayWorldHit` gives the surface normal), casings, sparks/dust per surface, explosions (fireball, shockwave, debris, scorch). Quality `alta` (bloom via EffectComposer + shadows; default with a mouse) or `baja` (default on touch), toggled in the HUD and remembered (`fuego.calidad`). Lights are pooled and created up front so no shader recompiles mid-game. `components/fuego/Controls.tsx`: mouse + keyboard with pointer lock, or touch (joystick, drag to look, the fire button also looks when dragged, aim toggle; scoped sniper = hold to aim, release to fire). In development `window.__fuego.give(weapon)` hands you a weapon for testing. Sounds in `lib/fuegoAudio.ts`.

## Gotchas

- RTDB silently drops `null`-valued keys and empty arrays/objects on write. Fields that may be null/empty may be *absent* at runtime — normalize on read as `subscribeRace` and memotest's `normalizeState` do.
- RTDB turns objects with numeric keys into arrays; key such maps with strings (memotest uses `c{index}`).
- Room codes are 6 characters and uppercased in each `[roomId]/page.tsx`; `params` is a Promise in this Next version.
